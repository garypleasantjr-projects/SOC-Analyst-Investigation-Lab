# SOC Analyst Investigation Lab

## Overview

This repository documents my hands-on SOC Analyst lab environment and security investigations using **Wazuh**, **Windows 11**, and **Ubuntu Server**.

The purpose of this lab is to develop practical experience with:

- Security event monitoring
- Windows Security logs
- SIEM alert investigation
- Authentication-event analysis
- Endpoint telemetry
- Event correlation
- Incident documentation

Rather than only learning security concepts theoretically, this lab allows me to generate controlled activity on an endpoint, observe how the operating system records it, and investigate how that activity appears inside a centralized SIEM platform.

---

## Lab Architecture

```text
Windows 11 Endpoint
        |
        | Wazuh Agent
        v
Ubuntu Server
        |
        | Wazuh Manager
        | Wazuh Indexer
        | Wazuh Dashboard
        v
SOC Investigation
```

### Windows 11 Endpoint

The Windows 11 virtual machine acts as the monitored endpoint.

- Operating System: Windows 11 Pro
- Endpoint Name: `Windows11EndpointVM`
- Wazuh Agent: v4.14.10
- Wazuh Agent ID: `001`
- Endpoint IP: `172.16.121.128`

The Wazuh agent collects security telemetry from the endpoint and forwards it to the Wazuh server for analysis.

### Wazuh Server

An Ubuntu Server virtual machine hosts the central Wazuh components.

The Wazuh environment includes:

- Wazuh Manager
- Wazuh Indexer
- Wazuh Dashboard

The dashboard is accessed through a web browser and is used to search, review, and investigate security alerts generated by the monitored endpoint.

# Investigation 01 — Windows Authentication Failures

## Objective

The goal of the first investigation was to generate controlled failed authentication attempts on the Windows 11 endpoint and determine whether those events could be:

1. Recorded by Windows
2. Collected by the Wazuh agent
3. Forwarded to the Wazuh server
4. Detected by Wazuh
5. Investigated through the Wazuh dashboard

---

## Test Scenario

A local Windows account named:

```text
TestUser
```

was created on the Windows 11 endpoint.

Multiple intentionally incorrect passwords were entered during interactive login attempts.

The activity was authorized and intentionally generated for this lab.

---

## Windows Security Event

Windows recorded the failed authentication attempts in the Security event log.

The relevant event was:

```text
Event ID: 4625
Description: An account failed to log on
```

Windows auditing was verified using:

```powershell
auditpol /get /subcategory:"Logon"
```

The system was configured to audit:

```text
Success and Failure
```

The failed authentication events were then located directly using PowerShell:

```powershell
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4625; StartTime=(Get-Date).AddMinutes(-30)} | Select-Object TimeCreated, Id, Message
```

This confirmed that Windows was successfully generating security telemetry for the failed login attempts.

---

## Wazuh Collection

The Wazuh agent configuration was checked to verify that the Windows Security event channel was being monitored.

The configuration contained:

```xml
<localfile>
    <location>Security</location>
    <log_format>eventchannel</log_format>
</localfile>
```

This confirmed that the Wazuh agent was configured to collect Windows Security events.

---

## Wazuh Detection

The failed login events were successfully forwarded to Wazuh and detected in the dashboard.

### Detection Details

```text
Agent: Windows11EndpointVM
Windows Event ID: 4625
Wazuh Rule ID: 60122
Rule Level: 5
Rule Description: Logon Failure - Unknown user or bad password
Target Account: TestUser
Logon Type: 2
Source Address: 127.0.0.1
Authentication Package: Negotiate
Logon Process: User32
```

Wazuh recorded six occurrences of the failed authentication event.

---

## Event Analysis

### Target Account

```text
TestUser
```

This was the local test account used during the controlled authentication test.

### Logon Type

```text
2
```

Logon Type 2 represents an **interactive logon**.

This is consistent with a user attempting to sign into the Windows system locally.

### Source Address

```text
127.0.0.1
```

`127.0.0.1` is the IPv4 loopback address.

This indicates that the activity originated locally from the Windows endpoint rather than from another system on the network.

### Failure Reason

```text
Unknown user name or bad password
```

The failed authentication events were expected because incorrect passwords were intentionally entered during testing.

## Analyst Assessment

### Classification

**Benign / Expected Activity**

### Reason

The failed login attempts were intentionally generated as part of an authorized SOC monitoring exercise.

There was no indication that the activity represented an actual unauthorized login attempt.

### Disposition

```text
Closed — Authorized Testing
```

## Key Findings

The investigation successfully demonstrated the complete security-monitoring pipeline:

```text
User Activity
    ↓
Windows Security Logging
    ↓
Wazuh Agent
    ↓
Wazuh Manager
    ↓
Wazuh Detection Rule
    ↓
Wazuh Dashboard
    ↓
Analyst Investigation
```

The lab confirmed that:

- Windows authentication failures were being audited.
- Event ID 4625 was generated correctly.
- The Wazuh agent was monitoring the Windows Security channel.
- Security events were successfully transmitted to the Wazuh server.
- Wazuh rule `60122` detected the authentication failures.
- Alert fields could be analyzed to determine the affected account, logon type, source, process, and failure reason.

---

## Timestamp Observation

During the investigation, a time difference was observed between timestamps displayed by Windows and timestamps shown in the Wazuh interface.

This demonstrated the importance of understanding:

- Local system time
- Time zones
- UTC timestamps
- SIEM timestamp normalization

Accurate timestamp interpretation is important when correlating events across multiple systems during a security investigation.
